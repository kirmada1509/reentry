# Automatic-agent Phase 3: progress and observed completion

Implemented October 23, 2026 (IST). ReEntry keeps a small evidence trail as you work, reconciles new requirements and can finish a purchase/application after a fresh matching confirmation. Start with [the automatic setup](AGENT_INFERENCE.md). [Interruption recovery and optional local reminders](AGENT_REMINDERS.md) are now available separately.

## Try the application journey

1. Run `./start.sh` and `pnpm sandbox:sites`. Reload the unpacked Chrome extension. Open [ReEntry](http://127.0.0.1:3000/observe), pair the browser, enable the printed Northstar site address and agree separately to automatic model processing.
2. Open the sandbox’s `application.html`. Use the fictional profile, write a sample statement, attach the simulated transcript, add the first referee and save the draft. ReEntry proposes an application task and an observed draft checkpoint without a task form.
3. Set `pnpm sandbox:switch v2` and reload the application. The second referee becomes required; your saved transcript and previous progress remain in the portal and in ReEntry’s evidence trail. The model updates the remaining action.
4. Open **Review application**. Trying **Submit fictional application** with a missing section shows validation, not success. Add the remaining referee and review again. Completing this sandbox creates a fictional browser-local receipt; it sends nothing externally.
5. The receipt can finish the matching uncorrected task. **Why this task?** shows timestamps and exact evidence. Refresh/restart retains task identity and progress. **Reopen task** starts fresh progress; earlier revisions remain in the ten-revision history.

For the shop, run `pnpm sandbox:commerce` and use the printed published demo credentials. Product research, cart, checkout validation, final overview and the upstream order confirmation are distinct states. No real payment or order is created. The agent observes your actions; it never presses the shop’s buttons for you.

## What the host verifies

The existing provider-independent model interface, LangGraph loop and SQLite effect transaction remain in place. First-discovered success pages create no new obligation. The host derives the allowed receipt subjects from current text; a generic success page permits only null, while same-stream review continuity establishes its identity. The model can propose a checkpoint with `upsert_task`, or request `complete_task` using an existing task ID, an earlier anchor event, a visible receipt subject (or null for a generic receipt), and host-issued source references. A complete proposal cannot set arbitrary task fields or operate a website.

- Task progress stores up to twelve entries, each linked to observation time, event ID, exact source quotes and an opaque browser stream. Prior progress remains evidence of what was seen then, not a claim that a later requirement is satisfied. Prompt memory includes the last three concise non-research progress entries with only kind/summary, without duplicating quotes or source metadata; more task history is an explicit bounded read. Redundant model-echoed event IDs/timestamps are accepted only if they exactly match the current observation, then replaced with host-owned metadata. Other extra checkpoint fields are rejected.
- The extension worker assigns a random tab-stream ID in browser session storage, after validating Chrome’s actual sender and page path. Sites and models cannot choose it. It survives worker suspension/navigation; browser exit/session replacement breaks completion continuity. Related tabs can still share a task, but a generic confirmation cannot borrow another tab’s checkout.
- A final review must visibly name the task subject and offer a final Submit/Finish action. Known validation/payment failures override an attempted-submission classification to blocked. A saved draft or a submit event alone is not success. If inference coalesced a fast review transition, the model can recover its observation through `inspect_history`; the host checks that actual review before accepting it. The request schema offers completion only when eligible same-task anchor IDs are available; otherwise the model must inspect history first. Up to sixteen source references are checked; only three quotes are retained.
- A completion requires an existing uncorrected purchase/application, same permitted origin/device/session/stream, a later receipt observed within two minutes, and an anchor no more than thirty minutes earlier. Positive English success wording and current receipt evidence are required. Named receipt subjects must match; other known task subjects cause rejection. Generic receipts require a direct transition to another page path with no intervening observation. Failures and cancelled checkouts break that chain.
- Hashes of previously observed success pages prevent replay of a known old receipt, including after raw observations expire. These hashes have no page bodies. Identical generic receipts from another legitimate purchase are conservatively rejected rather than assumed new. This is observation freshness, not a signed vendor-server verification or universal website support.
- Completed/cancelled tasks are terminal until reopened. Corrections retain the user’s goal/intent/finish condition; arbitrary corrected finish conditions require human judgment. **Mark finished** records an explicit user confirmation labelled **Marked finished by you**, separately from **Confirmation observed**. Neither action submits anything externally.
- Revision checks protect correction, reopening, finishing, dismissal and deletion. Deletion removes the task/history and purges inference contexts/proposals that might contain it. Minimal origin/path/time markers suppress delayed or repeated recreation; they can also suppress another task on the same shared path. **Disconnect and clear** resets this local automatic-agent data and requires pairing again. Shared raw observations follow their existing retention until clear; task deletion is not secure disk erasure.

Page text and model summaries are still untrusted. A malicious website can display deceptive success text, and a model can misunderstand it. The UI says **Confirmation observed**, not verified payment or institutional acceptance. Conservative gates deliberately leave unfamiliar, stale, ambiguous, cross-tab or corrected cases for review. Very brief page states may be missed by the debounced reader; no complete activity recording is promised. Provider outages and call budgets preserve existing tasks and show an unavailable/pending state.

## Verification commands

- `pnpm check`: project guards, transport/store/graph tests, negative completion cases, task deletion, restart and failed writes.
- `REENTRY_TEST_PRODUCTION=1 pnpm test:e2e`: production extension/web journeys, including `@progress` Northstar receipt/validation/changed-requirement/return, storage failure and axe/reflow.
- `pnpm test:commerce`: reused upstream shop regression; real inference is an explicit separate gate.
- `pnpm test:agent:progress <fresh-output.json>`: nine synthetic real-model progress/receipt/error cases. `pnpm test:agent:model <fresh-output.json>` retains the original eight-case inference regression plus two actual-reader final-review/receipt cases.
- `pnpm test:agent:live`: actual upstream shop → extension → backend → configured NVIDIA, from research through cart, validation, review, confirmation and restart. These explicit commands incur provider requests. CI uses deterministic model handlers.

Actual pass counts, retained development failures and unavailable native/manual acceptance are recorded in [TEST_RESULTS.md](TEST_RESULTS.md). NVIDIA remains the default; fresh real Ollama automatic-agent quality is not claimed.
