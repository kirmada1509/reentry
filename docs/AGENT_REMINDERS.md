# Automatic-agent Phase 4: returning to work

Implemented October 23, 2026 (IST). Phase 4 adds local return links, interruption summaries, explicit waiting, and optional Chrome reminders to [automatic tasks](AGENT_INFERENCE.md). The model still proposes next actions from observed evidence; a deterministic policy controls notification timing. No model/provider/framework dependency was added.

## Try it

1. Rebuild with `pnpm local:start` (stop the managed app first if it is running), reload the unpacked extension at `extension/.output/chrome-mv3`, and refresh open ReEntry/task pages. Preserve the same origin, extension ID and browser profile.
2. Open http://127.0.0.1:3000/observe and follow the existing browser/site/model setup. Browse the fictional Northstar application or reused local shop. A task acquires **Return to work** after the extension samples its enabled page. Sampling runs on navigation/focus changes, reconciliation and an approximately one-minute alarm.
3. Leave the task. After the configured away interval, its card shows where you left off: goal, last observed progress and current next action. Returning to an associated page produces a brief welcome-back state. These activity labels do not claim that work was completed.
4. Open **Return and reminder options** to mark **Waiting for something**, resume, snooze for one hour, or cancel/allow reminders for this task. Waiting remains an explicit user choice until resumed; merely visiting its page does not undo it. Reopening a finished task starts a fresh away interval.
5. Reminders start **off**. In the browser companion, open **Reminder settings**, enable gentle reminders and save. Chrome separately requests optional **notifications** and **idle** permissions. Declining does not enable the policy. Closing settings while that permission request is pending cancels the pending policy save. Configure quiet hours and an IANA timezone, such as `Asia/Kolkata`. Web settings can save the policy, but Chrome permission must still be allowed through the companion.

The default is **45 minutes away**, **at most one delivery attempt per task per local calendar day**, and **22:00–08:00 quiet hours**. The initial settings dialog offers the browser's timezone; the saved policy thereafter uses its explicit timezone. The interval can be 15–240 minutes. Only ongoing/uncertain purchases and applications qualify. Tentative candidates and research-only tasks are never reminder obligations. Waiting, snooze, per-task cancellation, completed/cancelled/dismissed/deleted tasks, paused observation/AI, changed model consent and revoked pairing suppress delivery.

## Local timing and delivery

The extension reuses Chrome alarms, notifications, idle detection and WXT storage. The existing SQLite authority stores versioned policy, activity and delivery reservations. No third-party scheduler, calendar/email integration or automation service is involved.

A visible, focused, enabled page is sampled as activity; with idle permission, a locked/idle machine is not considered active. Incognito tabs are excluded. Switching away briefly does not produce a reminder. On an unobserved/unsupported tab the extension sends no URL for that tab. Closed browser/server periods count as time away, but no notification is delivered until the local services are available again and current eligibility is checked.

The one-minute reconciliation alarm is recreated when missing on every worker start. It is a shared policy check, not one alarm per task. The server transaction reserves a stable task/local-day notification ID **before** returning a delivery instruction. The extension persists a matching attempt ID before calling Chrome, rechecks the current session/permission and asks the server to validate the task again immediately before the external effect. Successful Chrome API acknowledgement and failed creation are recorded separately; losing the acknowledgement does not falsely turn a successful create into a failure.

Ambiguous or failed attempts are **not resent that day**. A crash between reservation and display can therefore miss a notification; this is an intentional at-most-once attempt policy, not an exactly-once delivery guarantee. Snooze does not bypass the daily cap. A later day can become eligible again. Attempts are retained for up to 32 days on reconciliation; extension records contain only opaque hashes/times. Neither model text nor a website can override the schedule or give itself a notification tool.

The extension clears stale ReEntry notifications on reconciliation: completion, dismissal, deletion, waiting, snooze, returning to work, quiet hours, policy disable, permission/session changes or unavailable local connection. Companion actions also request immediate reconciliation. Web actions and fresh model completion are normally reconciled within about a minute while connected. A task can change in the brief gap between final validation and Chrome display; the next reconciliation clears it. Existing browser/system notification history and an unavailable browser are outside that cancellation guarantee.

Chrome/device sleep, browser exit, a stopped local server, network interruptions and OS notification settings may delay or prevent delivery. There is **no promise of notifications after browser exit**, waking a sleeping device, a visible OS banner, or repeated alerts until a task is done. Chrome may report API success even if the OS suppresses a banner. [Chrome alarm timing and persistence](https://developer.chrome.com/docs/extensions/reference/api/alarms), [notification API](https://developer.chrome.com/docs/extensions/reference/api/notifications), [idle API](https://developer.chrome.com/docs/extensions/reference/api/idle).

## Work links and privacy

Observation/model input retains its existing hashed-path protocol. A **separate authenticated local heartbeat** can store a return URL consisting only of `origin + pathname`; credentials are rejected, query strings/fragments removed, and scope, session, timestamp and pathname digest validated. These return URLs are never included in the model context or telemetry. Paths can still contain personal information, which is disclosed in site setup. Only enable sites you are comfortable recording.

The most recent task return path stays locally until task deletion or clearing automatic-agent data. The shared page lookup keeps up to 1,000 paths for at most 24 hours on reconciliation, including pending paths while AI task discovery finishes; activity/return metadata stays with the task. Task deletion also prunes unreferenced lookup paths. Deletion removes its recovery/delivery records transactionally; clearing agent data also disables/reset reminders and clears their local server records. Existing minimal delayed-recreation guards remain in force. This is logical deletion, not forensic secure erasure.

A path is a continuation aid, not an exact browser/form restoration. Query-driven/fragment-driven applications may open a general page instead. Several tasks on the same shared page path can all look active; this conservative page association does not establish attention to a particular product or field. Unsupported pages and inaccessible documents do not become observed by enabling reminders. The external site remains responsible for drafts, authentication and form state. A missing return link does not invent a destination.

Notification text is generic: **Your work is still here**. It contains no goal, site, form answer or next-action text. Clicking opens the local recovery home. No notification submits a form, places an order, marks completion or changes an external page.

## Deadlines and verification boundary

This phase schedules **interruption reminders only**. Website deadlines remain unknown to this scheduler; no date is extracted or inferred and no deadline reminder is scheduled. Adding deadline reminders later requires explicit evidence and an unambiguous timezone plus its own acceptance tests. Changed instructions/next actions continue through the Phase 3 evidence-linked model flow.

Deterministic tests cover clock/quiet-hour boundaries, timezone/DST, daily limits, fresh activity, waiting/snooze/cancel, finish/dismiss/delete, revoked sessions/consent, permission absence, conflicting settings, stale/forged URLs, failed writes, crash/ack ambiguity, safe notification content and missing-alarm reconciliation. Production browser tests exercise real app/extension transport, return links without query/fragment data, UI denial/cancellation handling at the permission boundary, persistence/restart and axe/narrow composition. Test-owned activity timestamps accelerate the 45-minute wait; there is no production clock override.

Headless Chromium cannot approve the native optional-permission prompt. The default production manifest is exercised without those permissions. Notification API acceptance uses a disposable copy of the production extension bundle whose test-only manifest predeclares notifications/idle; original assets/manifest and real user profiles remain unchanged. It calls the actual Chrome notification/alarm APIs and verifies the extension's tray records, dedup and cancellation. The grant/deny/cancel UI boundary also has controlled browser stubs. These are **not** proof of native permission-prompt approval or a visible desktop banner. Both remain manual gates, alongside native VoiceOver/side-panel/zoom acceptance. Exact test results are in [TEST_RESULTS.md](TEST_RESULTS.md).
